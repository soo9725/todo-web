# TODO 웹 앱 계획 (작성 2026-10-24, 마지막 갱신 2026-11-01)

새 세션에서는 이 파일(`docs/plan.md`)을 읽고 "다음 단계"부터 이어서 진행한다. 답변과 질문은 한글로 한다.

## 방향 전환 (중요)
이전 계획(iOS 앱, Expo, 잠금화면 위젯, Apple Developer)은 폐기했고(Mac 없음, 개인용), 지금 목표는 **Safari에서 열어 홈 화면에 추가해 앱처럼 쓰는 개인용 TODO 웹 앱**(웹사이트를 만들어 홈 화면 앱으로 띄움)이다.

## 확정한 설계 (/grill-me로 합의, 2026-10-25)
**이름·사용 환경**
- 앱 이름 "TODO", GitHub 저장소 이름 `todo-web`. 휴대폰 하나에서만 사용(개인용).
- 홈 화면 앱과 Safari 탭은 저장소가 분리될 수 있으므로 처음부터 홈 화면 앱으로만 쓴다.

**기술·배포**
- Vite + React + TypeScript + Tailwind CSS(4.3.3). Konsta UI는 쓰지 않는다(2026-10-25 결정: iOS 26식 모양을 거의 다 덮어써야 해서 Tailwind로 직접 만드는 쪽이 코드와 토큰이 덜 든다). 캘린더도 직접 구현.
- 윈도우 + VS Code에서 개발, 휴대폰은 같은 Wi-Fi로 접속해 확인. 배포는 GitHub Pages(공개 저장소도 https 무료. 비공개는 유료).
- 서버·로그인 없음. 일정은 브라우저 저장소(IndexedDB 등)에 저장, 오프라인에서도 열림(서비스 워커).
- 저장 코드(`src/storage.ts`) 규칙(확정):
  1. 읽을 수 없는 데이터(깨진 JSON, `version`이 1이 아니거나 `events`가 배열이 아닌 모양, 빈 문자열, `null`)는 원문 그대로 `todo-web:data-corrupt`에 보관하고, 빈 데이터를 돌려주며, 예외를 던지지 않는다. 원래 키(`todo-web:data`)는 지우지 않고 다음 저장 때 덮어쓴다.
  2. 손상이 두 번 나오면 보관본을 새 것으로 덮어쓴다(첫 번째 손상 데이터는 복구할 수 없게 된다).
  3. `saveData`는 검증 없이 저장한다(모양은 타입 검사가 지켜 준다).
  4. 과거 버전 마이그레이션은 하지 않는다. `version: 2`가 실제로 생길 때 만들고, 그 전까지 `version`이 1이 아닌 데이터는 1번처럼 보관한다.
  5. 저장 실패(용량 초과, 저장소 사용 불가)는 지금은 오류를 그대로 던진다. 사용자에게 알리는 방법은 일정 입력·수정 화면을 만드는 단계에서 정한다.
  6. 불러올 때 일정마다 `id`(문자열), `date`(문자열), `overrides`(객체)가 있는지 확인하고, 하나라도 틀리면 1번처럼 손상 데이터로 보관하고 빈 데이터를 돌려준다. 백업 가져오기를 만들 때도 같은 확인을 쓴다. 저장할 때의 검증은 하지 않는다(3번).
  7. 손상 데이터를 보관하는 쓰기가 실패해도 `loadData`는 오류를 던지지 않고 빈 데이터를 돌려주며 앱은 열린다. 이때 `getLoadIssue()`가 `'archive-failed'`를 돌려주고(그 밖에는 `null`), 화면이 생기면 사용자에게 "이전 데이터를 보관하지 못했다"고 알린다. 알리는 화면은 일정 입력·수정 단계에서 만든다. 원문이 보관되지 않은 채 다음 저장에서 덮어써질 수 있다(저장 공간이 꽉 찬 드문 경우).
- 백업: 하단 바의 `백업` 탭에서 한다(설정에는 없음). 항상 전체 일정을 파일 하나로 만들고 기간은 고르지 않는다. 내보내기는 공유 시트 → "파일에 저장"으로 하고, 저장 경로는 `iCloud Drive › TODO 백업` 폴더, 파일 이름은 `todo-backup-YYYY-MM-DD.json`(백업마다 새 파일이 쌓이고 오래된 것은 직접 지움). 웹 앱은 저장 경로를 강제할 수 없어서 사용자가 처음 한 번 폴더를 만들어 고르는 방식이다(다음부터 마지막 폴더가 기본으로 뜨는지는 실기기에서 확인). 가져오기는 지금 일정을 백업 내용으로 통째로 바꾼다. 마지막으로 **내보낸** 백업이 **7일 이상** 지났으면 캘린더 위 배너로 안내하고(배너 규칙은 "화면·디자인"), 일정이 하나도 없으면 "백업에서 가져오기"를 먼저 안내. 자동 예약 백업은 웹에서 불가능해 제외. 설정에서 웹 사이트 데이터를 지우면 일정이 사라질 수 있다.
- 미뤄 둔 이야기(사용자 요청): GitHub Pages 주소·저장소 공유 문제와 오프라인 앱 갱신(새 버전 배포 후 휴대폰에 옛 버전이 남는 문제)은 Pages를 만들 때 다시 논의한다.

**일정 항목**
- 필드: 제목, 메모, 날짜, 시간(선택), 색(4가지: 파랑·빨강·노랑·회색, 아래 "색 확정"), 중요(켜짐/꺼짐, 이전 이름은 우선순위), 완료 여부.
- 제목 표시: 시간이 있으면 `09:00 주간보고`, 없으면 `주간보고`. (`|`는 설명용 기호이므로 화면에 넣지 않는다.)
- 중요 표시한 일정은 제목 맨 앞에 색 점. 점 색은 일정 색별로 하나씩 정한다.
- 일정 색 값과 점 색은 "색 확정" 절의 값을 쓴다. 색 값은 한 파일(토큰)에 모아 둔다.
- 기간 일정: 시작일~종료일. 캘린더에 막대로 보이고 완료는 일정당 한 번. 시간은 시작일에만 표시하고, 나머지 날은 시간 없는 일정으로 취급해 정렬.
- 반복: 없음/매일/매주(요일 선택)/매월/매년. 종료는 "계속" 또는 종료 날짜. 기간 일정도 반복 가능(길이 유지). 반복되는 것은 규칙뿐이고, 순서·완료·개별 수정·이동은 그 날짜에만 적용된다(데이터는 "반복 규칙 하나 + 날짜별 예외 목록"). 수정·삭제는 "이 일정만 / 앞으로 전체".
- 삭제 확인: 반복 아닌 일정은 "삭제할까요?" 확인 창을 한 번 거친다. 반복 일정은 "이 일정만 / 앞으로 전체" 선택창이 확인을 겸하고 그 뒤에 추가 확인은 없다. 실행 취소는 없다.
- 기간 일정(예: 3일 출장)은 첫날에 완료해도 전체 기간이 회색 완료로 바뀐다.

**정렬과 완료**
- 같은 날 안의 기본 순서: 시간 있는 일정 시간순 → 시간 없는 일정 중 중요 표시한 것 → 나머지 → (아래 구역) 완료.
- 완료 체크: 일정 행 왼쪽의 ○를 누르면 완료(✓, 취소선 없음)가 되어 아래 "완료" 구역으로 내려가고, 완료에서 ✓를 다시 누르면 위로 올라온다. 날짜 시트(목업 2번)와 목록 탭(6·7번) 모두 같다. 목록 탭은 예정·완료 모두 월별이고, 예정에서 ○를 누르면 완료로, 완료에서 ✓를 누르면 예정으로 돌아간다.
- 마감 지난 일정: 기준은 시간이 아니라 날짜다. 시간이 지나도 그날 안이면 예정에 남고, 그날(기간 일정은 종료일)이 끝나면 자동으로 완료 쪽으로 넘어가 체크 없이 취소선으로 표시한다(빨간 표시는 없앴다). 행 오른쪽에 "복구" 버튼이 있고, 누르면 날짜와 시간을 새로 골라(오늘 이후만) 예정으로 돌아간다. 길게 누르면 "삭제" 메뉴만 뜨고, 삭제를 누르면 "삭제할까요?"를 묻는다(반복 일정이면 "이 일정만 / 앞으로 전체" 선택창). ○를 누르면 직접 완료(✓)로 바뀐다.
- 완료한 일정은 항상 미완료 일정과 **분리된 아래 구역**에 놓이고, 미완료 사이에 섞이지 않는다. 캘린더에서는 사라지지 않고 회색으로 바랜 모양으로 남는다(직접 완료는 작은 ✓, 마감 지남은 취소선).
- 순서 바꾸기: ≡를 길게 눌러 끌거나, 일정을 길게 눌러 메뉴의 "위로 이동 / 아래로 이동"을 고른다(끌기가 어려울 때의 대체 방법). 바꾼 순서는 날짜별로 저장. 완료 구역 안 순서도 조정 가능하나 미완료 위로 올라올 수 없다.

**화면·디자인**
- 월간 캘린더: 날짜 칸에는 점이나 표시를 넣지 않고, 날짜 밑에 일정이 색 막대와 줄인 제목으로 보인다. 칸당 3개까지, 넘치면 `+2`. 날짜를 누르면 아래 시트에 그날의 전체 목록. 목록 화면은 보조로 따로 두고, `+` 버튼으로 빠른 입력.
- 하단 바(5칸): 캘린더, 목록, 가운데 `+` 버튼, 백업, 설정(톱니바퀴 아이콘). 우선순위는 화면에서 "중요"라고만 부른다.
- 시간·날짜·반복 종료일은 휠 선택과 직접 입력 둘 다 가능. 반복은 목록에서 고르고, 매주는 요일 버튼. 구현 방식은 (가)로 확정: 숫자 입력칸 + 아이폰 기본 선택기(시간은 휠, 날짜는 달력 모양) 조합이라 휠을 직접 만들지 않는다. 직접 만드는 5칸 휠(나)은 쓰지 않는다.
- 캘린더는 일요일부터 시작으로 고정(설정 항목 없음).
- 설정 탭: 홈 화면에 추가하는 방법, 버전, **백업 버전**을 둔다(백업 기능과 한 주 시작 요일은 뺐다). 백업 버전 = 마지막으로 불러온 백업 파일 이름의 날짜(`todo-backup-YYYY-MM-DD.json`에서 뽑음), 불러온 적이 없으면 "없음". 7일 경과 배너와 백업 탭의 "마지막 내보내기"는 마지막으로 **내보낸** 날짜 기준(다른 값).
- 목록 탭의 예정은 월별로 보여 주고 ‹ ›로 달을 넘긴다. 목록에서 일정을 누르면 수정 / 다른 날에 붙여넣기 / 일정 삭제 메뉴가 뜨고, 삭제를 누르면 "삭제할까요?"를 한 번 더 묻는다.
- 캘린더 일정을 길게 누르면 메뉴(다른 날로 옮기기, 다른 날에 붙여넣기, 위로 이동, 아래로 이동, 수정, 삭제)가 뜨고, 그대로 끌면 다른 날짜로 옮겨진다. "다른 날에 붙여넣기"를 고르고 날짜를 누르면 "여기에 붙여넣기"로 새 일정을 만든다(원본 유지, 여러 날 연속 가능).
- 올라오는 화면(날짜 시트, 일정 없는 날, 일정 입력, 날짜·시간 선택, 일정 수정, 길게 누르기 메뉴, 목록 메뉴, 반복 삭제 선택, 삭제 확인)은 이전 화면이 어둡게 비치는 뒷배경 위에 뜬다. 일정 입력과 수정은 위에서 약간 떨어진 시트로 뜬다.
- 안전 영역: `viewport-fit=cover`를 넣고 `env(safe-area-inset-top/bottom)`으로 여백을 줘서 상태 표시줄·다이내믹 아일랜드·홈 바에 제목과 버튼이 가려지지 않게 한다(고정 숫자는 쓰지 않고 상태 표시줄 스타일은 구현 때 정함).
- 목업 1번의 62px 띠는 설명용이라 실제 앱에는 그려지지 않으며, 하단 탭 바는 바닥에서 20px 띄우고 구현에서는 하단 안전 영역 값을 더한다.
- 목업은 프로젝트의 `docs/mockup-color/`(확정 색, 22개 화면: `*.dc.html` + 배치 정보 `canvas.json`)이고 정지 그림이라 눌러도 동작하지 않는다. 화면: 1 월간 캘린더, 2 날짜 시트, 3 일정 입력, 4 날짜·시간 선택, 5 일정 수정, 6 목록 예정, 7 목록 완료, 8 목록 메뉴, 9 일정 없는 날, 10 첫 실행 안내, 11 백업 탭, 12 공유 시트, 13 파일에 저장, 14 설정, 15 길게 누르기 메뉴, 16 끌어서 옮기기, 17 다른 날에 붙여넣기, 18 반복 일정 삭제, 19 삭제 확인, 20 마감 지난 일정 복구, 21 마감 지난 일정 길게 누르기(삭제), 22 백업 배너를 닫은 뒤.
- 백업 배너(캘린더 맨 위): 마지막으로 내보낸 백업이 7일 이상 지났을 때 보이고, 오른쪽 끝의 작은 × 로 닫는다. 닫을 때 확인은 묻지 않고, 닫으면 배너가 있던 자리는 그냥 비어 달력이 위로 올라온다. **닫은 날(날짜 기준)에는 다시 뜨지 않고, 다음 날 접속하면 다시 뜬다**(백업을 내보내 7일 미만이 되면 뜨지 않음). 닫은 날짜는 브라우저 저장소에 저장(백업 파일에는 넣지 않음).
- 한국어만. 다크 모드는 앱에서 아예 뺀다(항상 밝은 화면). 글꼴은 시스템 글꼴(SF Pro, Apple SD Gothic Neo)만 쓰고 웹 글꼴은 받지 않는다. 아이콘 선 굵기는 2로 통일. 월간 캘린더 칸의 일정 글씨는 10px, 제목 글씨 크기는 그대로.
- 일정 색, 강조 파랑, 글씨 대비는 "색 확정" 절에서 정했다(강조 파랑은 애플 기본 `#007aff`).
- 움직임은 탭·끌기에 반응하는 것만 넣고 스크롤 등장 애니메이션은 넣지 않는다.
- 사용자 휴대폰은 iOS 26이고, 버튼과 탭 바는 iOS 26식(Liquid Glass 흉내)으로 확정했다. 하단 탭 바는 화면 아래에 떠 있는 반투명 캡슐(`backdrop-filter` 블러), 선택된 탭은 회색 캡슐 하이라이트. 취소·저장·완료 같은 상단 버튼과 큰 버튼은 캡슐형, 카드와 목록 행은 모서리를 크게(18~24), 시트는 가장자리에서 띄운 채 모서리 36, 알림창과 메뉴는 모서리 28. 진짜 Liquid Glass는 아니고 Safari에서 반투명 블러로 흉내 내는 것이다. Tailwind로 직접 만든다.

## 작업 방식과 자동화 (합의)
공통 규칙(단계 진행, 검증, 안전)은 전역 `CLAUDE.md`에 있고, 이 프로젝트 고유 규칙은 프로젝트 `CLAUDE.md`에 있다. 여기에는 이 프로젝트에 적용되는 합의 내용만 적는다.
- 단계 하나(구현 순서의 항목 하나)를 시작할 때 한 번만 "진행할까요?"를 묻고, 승인 뒤에는 구현, 검사, 오류 수정, 리뷰, 평가, 로컬 커밋을 묻지 않고 진행한다. 멈추는 경우는 헷갈림·결정 누락·계획과 목업 충돌, 검사 연속 3번 실패, 허용되지 않은 명령, 푸시다.
- 검사는 `npm run check`(타입 검사, oxlint, Vitest, 빌드)다. 소스가 바뀌면 Stop 훅이 자동으로 돌리고, 연속 3번 실패하면 멈춘다.
- 테스트는 `test-designer`(계획서만 보고 설계, 구현 내부는 보지 않음)가 쓰고, 구현자는 테스트를 고쳐서 통과시키지 않는다. 검사가 통과하면 `ponytail-reviewer`가 변경분을 리뷰하고, 지적을 고친 뒤 `step-evaluator`가 완료 기준, diff, 검사 결과, 스크린샷만 보고 판정한다. 세 에이전트 모두 opus로 고정했다. 리뷰나 평가를 쓰지 않았으면 보고서에 쓰지 않았다고 적는다.
- 새 규칙을 구현한 뒤에는 구현을 일부러 망가뜨려 테스트가 실패하는지 보는 변이 시험을 하고, 원래 구현으로 복원한 뒤 `cmp`로 같은지 확인한다.
- 화면은 UI가 생긴 단계부터 단계 끝에 Playwright로 확인하고, 모양은 스크린샷을 `docs/mockup-color/`와 비교한다. 즉석 확인은 Claude in Chrome으로 한다.
- 커밋은 검사가 통과할 때마다 자주 하고, 푸시는 단계가 끝날 때 승인받고 한 번 한다. 푸시 전에 가드 훅이 추적 파일의 개인 경로와 토큰을 검사한다.
- 실기기 확인은 일정 입력·수정·삭제를 만든 뒤, 끌기와 길게 누르기를 만든 뒤, 백업을 만든 뒤, Pages 배포 직후에 사용자에게 부탁한다. 안전 영역, 홈 화면 앱, 길게 누르기·끌기, 공유 시트 백업, 반투명 블러는 이 컴퓨터에서 확인할 수 없다.
- 입력을 기다릴 때 컴퓨터에 Windows 알림이 뜬다(전역 훅). 휴대폰 푸시는 설정은 켜져 있으나 도착하지 않았고 원인은 확인하지 못했다.
- **알려진 문제:** (1) 작업 폴더가 소문자 드라이브(`c:/...`)로 시작하면 Vitest가 "실행기를 못 찾음"으로 실패한다. Claude Code가 훅에 넘기는 `CLAUDE_PROJECT_DIR`가 이 표기라 Stop 훅에서 대문자로 맞춰 해결했다. 다른 도구가 소문자 경로로 Vitest를 직접 띄우면 다시 나올 수 있다. (2) 서브에이전트가 보고한 테스트 개수가 틀린 적이 있다(8개로 보고했으나 10개, 신규 20개로 보고했으나 18개). 개수는 `npm run test`를 실행해 직접 센다.
- **확인하지 못한 것:** `PowerShell(...)` 권한 규칙 문법이 적용되는지, Playwright의 WebKit과 Windows 동작, 휴대폰 푸시 도착. Playwright의 브라우저 본체는 사용자 폴더에 내려받아져서 아직 설치하지 않았고, 설치할 때 확인 창이 뜬다.
- **모델 비교(참고):** 같은 변경을 opus와 sonnet(미디엄)으로 리뷰시켰더니 판정(Ship)과 지적 대부분이 같았고, sonnet은 테스트 빈틈 두 가지를 더 찾고 opus는 화면 쪽 주의를 더 달았다. 표본이 하나이고 조건이 완전히 같지 않아 결론은 아니다. 다음 단계에서 몇 번 더 비교해 본다.
- 다른 세션(`todo-89`)을 다시 쓰기 전에 `git log`로 그 세션이 남긴 변경이 반영된 것을 확인한다.

## 구현 때 주의 (점검에서 나온 위험, 2026-10-25)
- 가장 어려운 부분: 반복 일정의 "규칙 + 날짜별 예외" 데이터 구조. 반복 계산은 `rrule`, 끌어서 순서 바꾸기는 `dnd-kit` 같은 무료 라이브러리를 쓸 수 있다고 알고 있으나 내용은 확인하지 못했다.
- 길게 누르기 + 끌기: 웹에 기본 기능이 없어 터치 동작을 직접 구현한다. 기본 길게 누르기(글자 선택, 미리보기)를 끄고 스크롤과 충돌하지 않게 해야 한다. 가장자리로 끌면 달을 넘기는 동작도 같은 종류.
- 월간 칸 안 일정 막대(여러 날에 걸친 막대, 칸당 3개와 `+n`)는 직접 만든다.
- 백업 내보내기는 홈 화면 앱에서 일반 파일 다운로드가 잘 안 되는 것으로 알고 있어 공유 시트로 하고, 실기기에서 확인한다.
- GitHub Pages 주소(`soo9725.github.io/todo-web/`)는 같은 계정의 다른 Pages 사이트와 브라우저 저장소를 공유하므로 저장소 이름을 고유하게 짓고, 앱 경로(base)와 서비스 워커 범위를 `/todo-web/`에 맞춘다. 사용자 요청으로 Pages를 만들 때 다시 논의.
- 서비스 워커: 새 버전을 올려도 휴대폰에 옛 버전이 남을 수 있어 "새 버전이 있어요" 안내가 필요하다(Pages 만들 때 논의).
- 다크 모드를 뺄 때 페이지에 "라이트만"(`color-scheme: light`)을 선언해야 아이폰이 다크일 때 입력칸이 어둡게 나오지 않는다.
- 기간·반복 단계 시작 때 결정: `overrides`의 키 규칙. 기간 일정(예: 3일 출장)의 날짜별 순서·완료, 다른 날로 이동한 반복 일정의 완료·순서를 어느 날짜 키에 둘지 정해져 있지 않다. 리뷰의 제안안은 "키는 그 일정이 화면에 나타나는 날짜, 기간 일정도 날마다 키를 쓴다, 이동한 반복 일정의 완료·순서는 원래 날짜 키에 둔다"이다. 확정 전까지 `types.ts`의 주석("반복이 아닌 일정은 시작 날짜 하나만 쓴다")은 계획서의 "순서는 날짜별 저장"과 다르다.
- 백업 단계에서 할 일: 손상된 이전 데이터(`todo-web:data-corrupt`)를 꺼낼 수 있게 백업 탭에 "손상된 이전 데이터 내보내기"를 둔다. Mac이 없어 개발자 도구로는 꺼낼 수 없어서, 이것이 없으면 보관 장치가 사실상 쓸모가 없다. 공유 시트 코드를 다시 쓴다.
- 미정 사례(필요해질 때 결정): `version`이 숫자가 아니거나 최상위가 배열·숫자 등일 때(지금 구현은 손상으로 보관), 정상 데이터에 알 수 없는 추가 필드가 있을 때(지금은 그대로 통과), 보관본이 이미 있는데 정상 로드가 보관본을 건드리지 않는지, 같은 손상 원문을 여러 번 읽을 때, `overrides`가 배열일 때(지금은 통과), `overrides` 안의 값과 `repeat`·`weekdays`의 모양(지금은 검사하지 않아 `{"2026-11-04": null}` 같은 값이 통과하고 반복 계산 코드가 읽는 순간 오류가 날 수 있다), `id`·`date`가 빈 문자열이거나 날짜 형식이 아닐 때(지금은 통과). 반복·기간 단계 시작 때 함께 정한다.
- 알림 화면을 만들 때 주의: `getLoadIssue()`는 `App`에서 `loadData()` 다음에 읽고 그 값을 화면 상태에 보관한다(`loadData`를 다시 부르면 지워지고, 먼저 읽으면 `null`). `'archive-failed'` 상태에서 사용자가 첫 일정을 저장하면 원문이 완전히 사라지므로 알림은 첫 저장 전에 보여 준다.
